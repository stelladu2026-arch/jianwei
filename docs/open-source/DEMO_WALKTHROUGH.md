# 免密钥演示阅读版

**本页使用源码中已有的虚构演示材料，不是真实访谈、真实用户或市场证据。** 只阅读本页不会调用模型，也不会产生服务费用。

## 你扮演的角色

你是一位独立开发者，正在考虑为 1–5 人的软件团队开发客户支持工具。本次只决定：是否值得开展问题访谈。

## 第一步：把想法变成问题

原想法：“做一个 AI 客服工具。”

研究问题：“小团队是否因为用户缺少版本和复现信息，在解决问题前反复追问？现有邮箱、FAQ 和回复模板是否已经够用？”

## 第二步：阅读支持与反对材料

以下均为演示人物：

| 编号 | 材料摘要 | 阅读时要注意 |
| --- | --- | --- |
| S1 | A 在版本发布后重复解释配置步骤 | 只来自一位人物，发生时点有限 |
| S2 | B 需要来回三封邮件确认浏览器和版本 | 具体问题是信息补全，不一定需要完整客服系统 |
| S3 | C 每周只有少量咨询，FAQ 和邮箱足够 | 这是重要反证，不能为支持方案而删除 |
| S4 | D 自述使用付费客服工具，仍手动整理复现步骤 | 具体预算、账单和采购者未核实 |
| S5 | A 补充：主要是更新之后才发生 | 与 S1 同一人物、同一线程，不增加独立客户数 |
| S6 | B 愿意在不迁移邮箱、提取准确的前提下试用 | 是有条件的兴趣，不是付款承诺 |

## 第三步：看一个有边界的判断

**建议先验证“第一轮补齐问题上下文”，不要直接投入完整客服系统。**

原因：材料中反复追问的信息比较具体，已有工具又可能足够。应先验证频率与收益，保留低咨询量团队的反证。

未知项：真实发生频率、每次耗时、跨团队是否重复、采购人、切换成本、付费意愿。

## 第四步：把判断变成行动

拟招募 5 位符合条件的人，让他们展示最近 3 次咨询，记录信息缺口、往返次数和处理时间。若至少 3 人出现重复追问并愿意提供脱敏样例，再开展一周人工信息补全试验。

这些人数是演示实验的设定，不是有效市场的通用门槛。尚未执行的动作不能写成结果。

## 第五步：什么时候需要回来更新判断

- 实际咨询量很低：缩小目标人群或暂缓。
- 问题频繁但现有模板已能解决：先改善模板，检验是否仍需工具。
- 人工试验持续节省时间且用户再次请求：再测试自动化与付费。

## 在应用里看什么

独立部署准备好后，加载“虚构演示项目”，核对研究范围、证据、机会卡和导出。模拟执行只帮助理解流程。真实研究需要另外配置模型，不能把模拟输出记入真实试用完成数。
